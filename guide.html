120.1・28%

120.1 存取、權限與安全

120.1.1 使用者與產品存取

帳、組、站、App、權Account → organization → site → app → Jira 權限。
Suspend 會回來、remove 要重來
  1. Atlassian account → organization → site → app一個帳號可以在多個 organization；app 存取（product access）才決定能不能用 Jira。
  2. Product access給使用者 app 角色（User、Admin…）＝加進該角色的 default group；佔授權的是有 User 角色的人。
  3. Managed vs external驗證 domain 並 claim 的帳號＝managed，可改資料、停用、刪除；其他都是 external user。
  4. Remove vs suspendRemove：移出 organization、要重新邀請並重設 group；Suspend：暫停、不計費，Restore 後角色與 group 回來。
  5. 刪除 group不會刪除使用者；用這個 group 設定的權限會失效；default group 不能刪。
  6. 匿名存取Permission scheme 把 Browse Projects 給 Public（Anyone on the web）；只有 company-managed 可以。
本節所有「本段必考」（7 條）
  • 沒有 product access 就不是 Jira 使用者，不能編輯、指派；Browse／Create 可給 Public 是例外。
  • Default group＝授權入口。
  • Approved domains＝同公司 domain 自助加入。
  • Suspend 可完整還原；remove 要重設。
  • 只有 managed account 能被 deactivate／delete。
  • 刪 group＝相關權限一起消失。
  • 匿名＝Browse Projects 給 Public，只有 CMP。

120.1.2 Admin 權限

組織管人、Jira 管設定、專案管自己三種 admin 各管各的。
  1. Org admin最高：管使用者、group、app 存取、安全政策；唯一能指派其他 org admin、site admin、Jira 的 app admin。
  2. Site admin管理 site 上的 app 與 Marketplace app；要有 Jira 授權才能用 Jira 功能。
  3. Jira admin（app admin）Administer Jira 全域權限；建 project、改 scheme、workflow、欄位。不能管使用者、不能匯入匯出、不能改系統 email。
  4. Project adminAdminister Projects 權限（CMP）或 Administrator role（TMP）；只管自己的 project。
  5. Org／site admin 與 Administer Jira原始介面要把自己加進 jira-administrators；集中式介面下 org admin 預設有各 app 的 app admin 角色（可被移除）。
  6. 用 group 授權 admin把人加進 admin 的 default group，例如 jira-admins-xxx、org-admins。
本節所有「本段必考」（3 條）
  • Jira admin 不能管使用者；可建立 backup，但匯入 backup 要 org admin。
  • Project admin 管 role 成員、不管 scheme。
  • Org admin 是唯一能指派 org、site、Jira app admin 的人。

120.1.3 Global permissions

管、看、分、訂、批、建Administer、Browse users、Share、Subscriptions、Bulk、Create TMP。
全站只給群組
  1. Administer JiraJira admin：建 project、改 issue type、欄位、workflow、scheme；不能管使用者、匯入匯出、系統 email。
  2. Browse users and groupsUser picker 與 @mention 看得到全站使用者；沒有的人只看得到在該 project 有 Browse 的人。
  3. Share dashboards and filters能把 filter、dashboard 分享給其他人。
  4. Manage group filter subscriptions能建立、刪除給 group 的 filter subscription。
  5. Make bulk changesBulk 編輯、移動、刪除、轉換（還要 project 權限）。
  6. Create team-managed projects只能建 TMP；建 CMP 要 Administer Jira。
本節所有「本段必考」（4 條）
  • Bulk change 要 global＋project 兩層。
  • Browse users and groups 影響 @mention 範圍。
  • Global permission → 只能 group。
  • 五道關卡要全部通過。

120.1.4 Project permissions

因專案而異用 role全站一致用 group。
權限成對記Assign＋Assignable、Move＋Create、Link＋全站。
  1. CMP：permission schemeJira admin 建 scheme、把權限給 role、group、user、reporter、assignee、project lead、user／group custom field、Application access、Public。
  2. TMP：access level＋roleOpen／Limited／Private＋Viewer／Member／Administrator（與自訂 role）；project admin 自己管。
  3. Role vs groupRole 讓同一個 scheme 用在多個 project、由 project admin 管成員；group 是全站、由 org admin 管。
  4. 權限要成對Assign Issues＋Assignable User；Resolve Issues＋Transition；Move Issues＋目標 project 的 Create；Link Issues＋全站開 issue linking。
  5. User custom field把權限給「欄位裡的人」，例如 Approver 欄位的人可以 Transition。
  6. Project adminAdminister Projects：管 role 成員、components、versions、details；不能改 scheme。
本節所有「本段必考」（4 條）
  • Scheme 由 Jira admin 改，可多 project 共用。
  • 給 role 才能讓 project admin 自己管人。
  • Assign＋Assignable；Move＋目標 Create；Link＋全站 linking。
  • 權限因 project 而異 → role；全站一致 → group。

120.1.5 Issue-level security

方案、等級、成員、預設、套用啟用五步。
子隨父Sub-task 繼承 level。
記得 Reporter
  1. 組成Issue security scheme（Jira admin）→ security levels → 每個 level 的成員。
  2. 成員類型Reporter、Current assignee、Project lead、project role、group、single user、user／group custom field、Application access、Public。
  3. 啟用四步建 scheme → 建 level 並加成員 → 設 default level（選用）→ 套到 project（並把 Security Level 欄位放上 screen）。
  4. 誰能設 level有 Set Issue Security 權限的人；只能選自己是成員的 level（Jira Server 文件 Setting Security on an Issue 明載；Cloud 文件未寫）。
  5. Sub-task 繼承Sub-task 用 parent 的 security level，不能單獨設。
  6. TMP沒有 security scheme；可以把某個 issue type 限制給特定 role 看（Restrict access to an issue type）。
本節所有「本段必考」（4 條）
  • Issue 只能一個 level。
  • 沒設 level 的 issue，有 Browse 的人都看得到。
  • Level 記得加 Reporter。
  • 留言可限制可見性；TMP 用 issue type 限制。
120.2・11%

120.2 專案一般設定

120.2.1 Project 類型與 template

先管理、再工作CMP／TMP，然後 Scrum／Kanban。
共用一份、牽一髮動全身
  1. Company-managed（CMP）設定是 scheme、可跨 project 共用；Jira admin 管；有 components、issue security、多 board、匿名存取。
  2. Team-managed（TMP）設定長在 project 裡、project admin 自己改；一個 board；沒有 components、issue security、匿名存取。
  3. TemplateScrum（sprint、backlog、velocity）vs Kanban（連續流、WIP）；也有 business、service 的 template。
  4. 建 CMP 要 Jira adminTMP 有 Create team-managed projects 全域權限的人就能建。
  5. Share settings with an existing project建 CMP 時直接沿用另一個 project 的所有 scheme；改一次全部跟著變。
  6. TMP 的設定不能共用每個 TMP 各自一份。
本節所有「本段必考」（3 條）
  • 管理方式（CMP／TMP）與工作方式（Scrum／Kanban）是兩個選擇。
  • 共用＝改一次影響全部。
  • TMP 不能共用設定。

120.2.2 Project details

名、網、圖、述、主、派Project admin 改得到的六個欄位。
Key 換了、舊的還在
  1. Project admin 能改Name、URL、Avatar、Description、Project lead、Default assignee。
  2. Project admin 不能改Key 與 Category（Jira admin；key 也可由 org、site admin 改）。
  3. 改名自動更新所有 filter 中的名稱。
  4. 改 key舊 key 存成 previous key，舊連結、filter、JQL 繼續有效；舊 key 不能被新 project 使用；description 裡的文字別名不會被改。
  5. Default assignee只有 Unassigned 或 Project lead。
  6. 側欄（sidebar）Project admin 可調整導覽：隱藏或顯示功能、加 shortcuts。
本節所有「本段必考」（3 條）
  • Key、category → Jira admin。
  • Default assignee：Unassigned 或 project lead。
  • 改 key 安全：舊 key 變 alias。

120.2.3 Versions

發、併、刪、封Release、merge、delete、archive。
未完成：移走或忽略
  1. Fix version這張 issue 會在哪個版本完成；Affects version：問題出現在哪個版本。
  2. 名稱在 project 內唯一同一個 project 不能有兩個同名 version。
  3. Release 時有未解決的 issue選擇移到另一個 version，或忽略並照樣發布。
  4. Merge把多個 version 的 issue 併到一個 version；被併的 version 會刪除。
  5. Delete要決定 Fix／Affects version 的 issue 改指到哪個 version，或直接移除。
  6. Scrum vs KanbanScrum 先規劃再發布；Kanban 隨時發布已完成的工作，發布時才命名。
本節所有「本段必考」（3 條）
  • Release 有未完成 → 移走或忽略。
  • Merge 後來源 version 消失。
  • 名稱在 project 內唯一。

120.2.4 Components 與自動指派

元件、專案、空、預設Component lead＞Project lead＞Unassigned＞Project default。
  1. Component只在 CMP；依功能、部門或工作流分組；project admin 建立。
  2. Component 的 default assigneeProject default、Component lead、Project lead、Unassigned。
  3. 多個 component先比類型：Component lead ＞ Project lead ＞ Unassigned ＞ Project default；多個 component 都是 Component lead 時，依 component 名稱字母序（不是 lead 的名字）。
  4. 沒有 component用 project 的 default assignee（Unassigned 或 project lead）。
  5. 被指派的人要 Assignable User沒有就跳過。
  6. Unassigned 選不到全站的 Allow unassigned issues 關閉時。
本節所有「本段必考」（3 條）
  • 類型先、字母後。
  • Project default 類型最低。
  • Component lead 也要有 Assignable User。
120.3・18%

120.3 Issue type、欄位與畫面

120.3.1 Issue types

型選、流、畫、欄Issue type scheme 選型；workflow、screen、field config 三個 scheme 各管一塊。
改名全站
  1. Issue type 是全站物件Settings → Issues → Issue types；改名會影響所有使用它的 project。
  2. Issue type scheme決定一個 project 有哪些 issue type、順序與預設值；可多 project 共用。
  3. CMP 對應Issue type 透過 workflow scheme、issue type screen scheme、field configuration scheme 各自對應 workflow、screen、欄位行為。
  4. Sub-task全站開關（Settings → Issues → Sub-tasks）；sub-task 的工時可彙總到 parent（Include sub-tasks）。
  5. Epic跨 sprint 的大工作；CMP 的 epic 可以有其他 project 的 child（cross-project epic）。
  6. TMPProject admin 在 Project settings → Issue types 直接建，欄位拖拉加入。
本節所有「本段必考」（5 條）
  • 新增 issue type 到 project＝加進它的 issue type scheme。
  • Issue type 名稱是全站的。
  • 移除使用中的 type 要先 migrate issue。
  • Sub-task 工時可彙總到 parent。
  • Cross-project epic 只在 CMP。

120.3.2 Fields

在哪、在不在、藏不藏Context、screen、field configuration。
一案一境一個 project 只屬於一個 context。
  1. Custom field 是全站物件Jira admin 建立；選類型、名稱、context、要放上哪些 screen。
  2. Context決定欄位在哪些 project 與 issue type 出現、預設值、選項；同一個 project 只能屬於一個 context。
  3. Field configuration決定欄位行為：description、Required、Hidden、renderer（wiki 或純文字）、可用的 screen。
  4. Field configuration scheme依 issue type 套用不同 field configuration。
  5. 欄位沒出現？查三件事：context（project／issue type）、screen 上有沒有、field configuration 有沒有 hide。
  6. TMPProject admin 在 issue type 上拖拉欄位；建的欄位只在該 project。
本節所有「本段必考」（5 條）
  • 不同 project 要不同選項 → 多個 context。
  • Hide 比 screen 優先。
  • 依 issue type 不同行為 → field configuration scheme。
  • Context → screen → field configuration。
  • TMP 欄位不共用。

120.3.3 Screens 與 issue layout

型→方案→畫面→排版Issue type screen scheme → screen scheme → screen → layout。
建、改、看Create、Edit、View 三個操作。
  1. Screen一組欄位（可有 tabs）；Jira admin 建立。
  2. Screen scheme依操作對應 screen：Create、Edit、View。
  3. Issue type screen scheme依 issue type 對應 screen scheme；套到 project。
  4. Transition screenWorkflow transition 上也可以掛 screen（例如 Resolve 時填 resolution）。
  5. Issue layoutProject admin 決定欄位在 issue view 的 description、context（含 hide when empty）、hidden 區。
  6. Copy issue layoutJira admin 可把 layout 複製到使用同一個 screen 的其他 project（覆蓋、不連動）。
本節所有「本段必考」（4 條）
  • Create／Edit／View 可以各用不同 screen。
  • Layout 只排列、不新增欄位。
  • Copy layout 會覆蓋、不連動。
  • TMP 用 issue type 設定欄位，沒有 screen scheme。
120.4・14%

120.4 Workflow 與 automation

120.4.1 CMP workflows

條件藏、驗證擋、後置做Condition、validator、post function。
回頭要清 resolution
  1. Status 是全站物件有 category：To Do、In Progress、Done（決定顏色與報表）。
  2. Transition兩個 status 之間的路；可掛 screen、properties、conditions、validators、post functions。
  3. Condition → validator → post functionCondition 決定按鈕出不出現；validator 在提交時檢查；post function 在通過後自動做事。
  4. Resolution 很重要有 resolution＝已解決；用 transition screen 或 post function（Update issue field）設定，reopen 時清空。
  5. Board 與 statusBoard 欄位對應 status；workflow 加了新 status 卻沒 map 到欄位，issue 會從 board 消失。
  6. Custom event在 post function 觸發自訂 event，notification scheme 再依 event 寄信。
本節所有「本段必考」（5 條）
  • Condition 藏按鈕；validator 擋提交；post function 事後做。
  • Resolution 有值＝已解決。
  • Reopen 要清 resolution。
  • 新 status 要記得 map 到 board 欄位。
  • jira.issue.editable=false 讓 status 不可編輯。

120.4.2 TMP workflows

限四、更三Restrict 類 4 條（含驗證權限）、Update 類 3 條。
  1. 每個 issue type 各自的 workflowProject settings → Issue types → 選 type → Edit workflow。
  2. Status 與 board 欄位連動在 board 加一欄＝加一個 status；status 的 category 決定 To do、In progress、Done。
  3. Transitions可以從任何 status（Any status）或指定 status 轉入。
  4. Rules：restrict限制誰能移動（assignee、reporter、user、role、group、permission）、要經過某 status、欄位值條件、驗證權限。
  5. Rules：update自動指派（reporter、current user、no one、某人）、更新欄位、複製欄位值。
  6. 必填欄位最可靠：在 work type 的欄位勾 Required（建立時就必填）。官方兩頁 rule 清單不一致：Available workflow rules 頁沒有必填類 rule，Add or remove workflow rules 頁另列 Remind people to update empty fields。
本節所有「本段必考」（2 條）
  • TMP 的 rule 對應 CMP 的 condition／validator／post function。
  • TMP 改 status 名只影響自己。

120.4.3 Automation rules

觸、條、枝、動Trigger、condition、branch、action。
Actor 要有權
  1. ScopeProject rule（project admin 可建）vs global／multi-project rule（Jira admin）。
  2. Trigger只能一個：created、transitioned、field value changed、scheduled、manual…
  3. ConditionIssue fields、JQL、user、related issues、{{smart values}}、If/else。
  4. Branch對 related issues（sub-tasks、parent、linked、JQL 結果）各跑一次。
  5. Smart values{{issue.summary}}、{{issue.parent.key}}、{{now.plusDays(1)}}、{{triggerIssue}}。
  6. Actor 與權限Rule 以 actor（預設 Automation for Jira）執行；actor 要有 project 權限，rule 才改得動 issue。
本節所有「本段必考」（5 條）
  • 相關 issue → branch。
  • 一條 rule 一個 trigger。
  • Actor 沒權限 → rule 失敗。
  • Global rule 要 Jira admin。
  • Branch 內用 {{triggerIssue}} 取原始 issue。
120.5・8%

120.5 通知

120.5.1 CMP notification scheme

事件、方案、權限、個人四關都過才收得到。
特定轉換寄信靠自訂事件
  1. Notification schemeJira admin 建立；每個 event 對應收件人；可多 project 共用。
  2. System eventsIssue Created、Updated、Assigned、Resolved、Closed、Commented、Comment Edited、Reopened、Deleted、Moved、Work Logged、Generic Event…
  3. Workflow transition 觸發 eventTransition 的 post function 決定觸發哪個 event（例如 Resolve → Issue Resolved）。
  4. Custom eventSettings → System → Events 建立 → transition post function 觸發 → scheme 設收件人。
  5. 收件人類型Current assignee、Reporter、Current user、Project lead、Component lead、All watchers、user、group、project role、user／group custom field。
  6. 收件人要有權限看不到 issue 的人（Browse、issue security）不會收到。
本節所有「本段必考」（2 條）
  • 收件人＝scheme 設定 ∩ 有權限 ∩ 個人沒關掉。
  • 要針對特定 transition 寄信 → custom event。

120.5.2 TMP 通知

自己的通知自己設TMP 不用 scheme。
  1. 位置Space settings → Notifications → Add notification（需要 Administrator role）。
  2. 事件Created、assigned、updated、commented、moved、comment edited、deleted、work logged、worklog updated、comment deleted、worklog deleted。
  3. 收件人All watchers、current assignee、current user、reporter、project lead、project role。
  4. 寄件 email可以改這個 project 通知的寄件 email address。
  5. 刪 role 的影響用到該 role 的通知會失效，要手動移除。
  6. 個人設定一樣適用使用者可以關掉部分通知。
本節所有「本段必考」（1 條）
  • TMP 通知由 project admin 設，不共用。

120.5.3 個人通知設定

個人是濾網只能少、不能多。
  1. 位置右上 Settings → Personal Jira settings → Notification settings（與 General settings）。
  2. 濾網個人設定疊在 admin 設定之上：可以少收，不能多收 admin 沒設定的通知。
  3. 可選Watching、reporter、assignee、被 mention、自己做的變更；也可全關 email。
  4. Watch your work items開啟後，自己建立或留言的 issue 會自動 watch。
  5. 摘要信零碎更新最多延遲 10 分鐘合併成一封；mention、指派、SLA 等重要通知立即寄。
  6. 每個 project 可客製最多 50 個 space 各自設定。
本節所有「本段必考」（2 條）
  • 個人設定只能少收。
  • 自己改的預設不通知自己。

120.5.4 Mail handlers

有鑰留言、無鑰開單主旨的 issue key 決定。
CC、To、BCCCC assignee 的順序。
  1. 設定位置Settings → System → Mail → Incoming Mail：先有 mail server（Google、Microsoft 用 OAuth；或 POP／IMAP），再加 mail handler。
  2. Handler 類型Create or comment（主旨有 issue key 就留言，沒有就建 issue）、只建 issue、只留言（全文、去除引用、marker 之前）。
  3. Default reporter寄件人不是 Jira 使用者時用這個帳號當 reporter（要有 Create Issues）；原寄件人寫在 description 末尾。
  4. CC assignee指派給第一個 CC 的使用者；沒有就看 To、再看 BCC；都沒有就不由 handler 指派。
  5. 其他選項Project、issue type、strip quotes、catch email address、bulk（ignore／forward／delete／accept）、forward email、CC watchers。
  6. 限制超過 7 天的信不處理；SPF 驗證失敗會被拒。
本節所有「本段必考」（3 條）
  • 主旨有 key → 留言。
  • Default reporter 讓非使用者也能建單。
  • 沒 assignee → 看 CC assignee，再看 project default。
120.6・12%

120.6 進階使用者功能

120.6.1 進階 JQL

欄、算、值、連、排Field、operator、value、keyword、ORDER BY。
有 OR 就加括號官方：沒有括號時由左到右計算。
  1. 結構field operator value，用 AND、OR、NOT 連接，ORDER BY 排序；括號決定優先順序。
  2. Custom field用名稱（"Story Points"）或 cf[10010]；名稱有空白要加引號。
  3. 常用 operator=、!=、IN、NOT IN、~（文字包含）、IS EMPTY、WAS、CHANGED、>、<。
  4. 常用 functioncurrentUser()、membersOf()、startOfWeek()、endOfMonth()、now()、openSprints()、releasedVersions()、linkedIssues()。
  5. 日期created >= -7d、resolved >= startOfMonth()、duedate < now() AND resolution = Unresolved。
  6. Basic search 的限制不能用 OR 組合不同欄位、不能用括號、不能用 WAS／CHANGED 等歷史查詢。
本節所有「本段必考」（5 條）
  • 官方：沒有括號時由左到右計算；有 OR 就加括號。
  • WAS 含建立時的值；CHANGED 只看有改過的。
  • startOfMonth(-1)＝上個月第一天。
  • 未解決用 resolution = Unresolved。
  • 要 OR、括號、歷史 → JQL。

120.6.2 Filters、dashboards、subscriptions

分享看權限、訂閱看個人結果永遠依收件人的權限。
  1. 分享要權限Share dashboards and filters 全域權限；可分享給 user、group、project（role）、組織、public。
  2. 看到的結果因人而異被分享的人只看得到自己有權限的 issue。
  3. SubscriptionFilter → Subscribe：寄給自己或 group；排程 daily、days per week、days per month、advanced（cron）；可選沒結果也寄。
  4. 訂閱給 group要 Manage group filter subscriptions，且只能選自己是成員的 group；每位成員依自己的權限收到結果；信中只列前 200 筆。
  5. currentUser() 在訂閱依每位收件人分別計算：每個人收到「自己的」清單。
  6. Default dashboardJira admin 設定；每個人預設看到它，可以自己另建。
本節所有「本段必考」（5 條）
  • 分享 filter 不等於給權限。
  • currentUser() 依收件人分別計算。
  • Group 訂閱要 Manage group filter subscriptions。
  • 兩個欄位交叉用 Two Dimensional；一個欄位用 Pie Chart。
  • Gadget 的內容受 filter 分享與 Browse 權限限制。

120.6.3 Bulk operations

編、轉、移、刪、看五種 bulk 操作。
一千為限、一轉一次
  1. 權限Make bulk changes 全域權限＋每個動作對應的 project 權限（Edit、Transition、Move、Delete…）。
  2. 上限一次最多 1,000 個 issue。
  3. 五種操作Edit、Transition、Move、Delete、Watch／Unwatch。
  4. Transition一次只能一個 transition；不同 workflow 的 issue 要分組；要填 transition 要求的欄位。
  5. 通知可取消勾選 Send mail for this update（不是每種操作都有）。
  6. Move要對應 status 與欄位；CMP → TMP 會永久失去 components 與 versions。
本節所有「本段必考」（3 條）
  • Make bulk changes＋project 權限。
  • 多值欄位注意 replace 與 add。
  • CMP → TMP：components、versions 永久消失。
120.7・9%

120.7 系統管理

120.7.1 全站介面設定

預設給新人、個人自己改
Banner 公私都行
  1. Look and feelSettings → System → Look and feel：logo、site title、顏色（Jira admin）。
  2. Announcement bannerSystem → Announcement banner：全站頂端訊息；可設 public（含匿名）或 private（只給登入者）。
  3. User default settings帳號建立時套用的預設：Email format、Work items per page、Default access（filter／dashboard 預設 public 或 private）、Notify users of their own changes、Autowatch own work items。
  4. Default vs personalDefault 只在帳號建立時套用；使用者之後可自己改。唯一例外：Email format 旁的 Apply 會強制所有使用者使用該格式，且使用者不能再改。
  5. Default dashboardJira admin 編輯（System dashboard）；沒自建 dashboard 的人看到它；匿名使用者也看這個。
  6. General configurationSite 名稱、預設語言、時區、Allow unassigned issues 等。
本節所有「本段必考」（4 條）
  • Banner 可 public 或 private。
  • Default 只在建立帳號時套用。
  • Email format 的 Apply＝強制全體、使用者不能改。
  • Default dashboard 只有 Jira admin 能改。

120.7.2 附件、連結、time tracking

附、連、App、時Attachments、linking、app links、time tracking。
關掉不刪
  1. Attachments全站開關與大小上限（Settings → System → Attachments）；還要 Create Attachments 權限。
  2. Issue linking全站開關＋link types（outward、inward 描述，例如 blocks／is blocked by）；還要 Link Issues 權限。
  3. Application links連到 Confluence、其他 Atlassian 或第三方產品，讓兩邊互相顯示資料。
  4. App navigator 連結在 app switcher 加自訂連結。
  5. Time trackingSettings → Work items → Time tracking：每天幾小時、每週幾天、顯示格式、預設單位；停用或重新啟用都不會遺失資料。
  6. EstimationBoard 的 estimation statistic（story points 或 time）與 time tracking 是不同設定。
本節所有「本段必考」（3 條）
  • Link Issues 權限＋全站 linking 都要開。
  • Time tracking 關掉不刪資料。
  • Hours per day 影響換算。

120.7.3 Status、resolution、priority

狀、解、優都全站改名大家都看到。
TMP 例外
  1. 建立Settings → Issues → Statuses／Resolutions／Priorities（Jira admin）。
  2. 改名影響全站CMP 的 status、resolution、priority 改名，所有使用它的 project、filter、board 都看到新名稱。
  3. TMP status屬於該 project，改名只影響自己。
  4. Resolution可設 default；有值＝已解決；不要放 create screen。
  5. Priority scheme不同 project 可以用不同 priority 清單。
  6. 停用 sub-tasksSettings → Issues → Sub-tasks；有 sub-task 存在時要先轉成 standard type。
本節所有「本段必考」（2 條）
  • CMP 的 status／resolution／priority 是全站共用。
  • TMP status 改名只影響自己。

120.7.4 Backup 與 import

備份不含自動化Automation 要另外匯出。
整站匯入會覆蓋CSV 只是新增。
  1. Backup managerSettings → System → Backup manager → Create backup for cloud；可勾附件、avatar、logo。
  2. 頻率含附件時兩次 backup 至少間隔 48 小時。
  3. 包含Issue 與欄位、board／sprint、使用者與 group、留言、設定（workflow、scheme、screen…）、archived projects。
  4. 不包含Automation rules（要另外匯出）、第三方 app 資料、Opsgenie 功能、Assets、app access 設定。
  5. 誰能做建立 backup：Jira admin 或 org admin；匯入 backup（覆蓋整站）：org admin（官方 Learning 課程）。
  6. Restore（匯入 backup）會覆蓋站上所有資料；Atlassian Backup & Restore 只能還原到沒有資料的 app、30 天內的 backup。
  7. 其他匯入CSV／JSON 匯入到新的或現有 project（CSV 有 Work Item Key 時會更新既有 issue）；Trello 每個 board 建一個新的 TMP（需 org admin）。
本節所有「本段必考」（3 條）
  • Automation rules 不在 backup 裡。
  • 含附件 48 小時一次。
  • Site import＝覆蓋；CSV／JSON＝新增。
