Issue-level security

3 分鐘速覽

Issue security：同一個 project 裡，不同 issue 給不同人看

  1. 組成Issue security scheme（Jira admin）→ security levels → 每個 level 的成員。
  2. 成員類型Reporter、Current assignee、Project lead、project role、group、single user、user／group custom field、Application access、Public。
  3. 啟用四步建 scheme → 建 level 並加成員 → 設 default level（選用）→ 套到 project（並把 Security Level 欄位放上 screen）。
  4. 誰能設 level有 Set Issue Security 權限的人；只能選自己是成員的 level（Jira Server 文件 Setting Security on an Issue 明載；Cloud 文件未寫）。
  5. Sub-task 繼承Sub-task 用 parent 的 security level，不能單獨設。
  6. TMP沒有 security scheme；可以把某個 issue type 限制給特定 role 看（Restrict access to an issue type）。
資料來源（5）有疑慮時點開看官方原文

  • Grant users access to security levels in a work item security schemeOnce you’ve created your work item security scheme, you’ll need to define which users can access each security level.
  • What are work item security schemes?users need to have the Set work item security permission.
  • What are work item security schemes?spaces need to have the Work item security field included on their Layout page.
  • Set up work types in team-managed spacesAnd, you can restrict who sees that type of work to specific roles in your space.
結構

Scheme、level、成員

  1. 建 schemeSettings → Issues → Issue security schemes → Add。
  2. 建 level加 level（例如 Internal、HR only），可設 default。
  3. 加成員每個 level 加 reporter、role、group、user custom field…（Administer Jira）。
  4. 套用Project settings → Issue security → 選 scheme；已有 issue 時要對應舊 level 到新 level。
  5. 讓人能設Permission scheme 給 Set Issue Security；並把 Security Level 欄位放到 screen。
本段必考
  • Issue 只能一個 level。
  • 沒設 level 的 issue，有 Browse 的人都看得到。

用法

常見情境

需求Level 成員
客戶回報的 bug 只給內部與回報者看Role: Developers＋Reporter
HR 案件只給 HR 與當事人Group: hr-team＋Reporter＋Current assignee
由欄位指定的審核者也能看User custom field value: Reviewer
Project lead 永遠看得到Project lead
  • Reporter 很重要：level 不含 reporter，提出 issue 的人建立後就看不到。
  • 移動 issue 到另一個 project 時，會套用新 project 的 default level；新 project 沒有 scheme 就等於公開給有 Browse 的人。
  • 留言權限：留言可以限制只給某個 role 或 group 看，這是單則留言層級，不是 issue security；能否選 group 取決於全站 Comment visibility 設定（Groups & Project Roles 或 Project Roles only），且只能選自己所屬的 role／group。
  • TMP：Space settings → Work types → 某 issue type → Restrict access：只有選定的 role 看得到這個類型的 issue（沒有 scheme、沒有 level）；只影響之後新建的 issue，Free 方案不能用。
本段必考
  • Level 記得加 Reporter。
  • 留言可限制可見性；TMP 用 issue type 限制。

動手做

實作 Lab：建一個「HR only」的 issue security level

約 30 分鐘Jira admin；Standard 以上（Free 不能用 issue security）

第一次做 Lab？先看 Lab 環境準備：用測試站台、準備測試帳號。畫面名稱可能隨 Atlassian 更新而不同，以下以現行畫面為準。

目標：從零建立 issue security scheme、level 與成員，套到 WEB，再用 Kim 和 Ana 的視角驗證誰看得到。

這個 Lab 對應的考點

啟用要建 scheme → 建 level 加成員 →（選用）default → 套到 project → 給 Set Issue Security 並把欄位放上 screen；level 要記得加 Reporter；sub-task 跟 parent。

準備

  • Ana 在 hr-team；Ana 與 Kim 都在 WEB 有 Browse Projects（例如在 Users role）。
  • WEB 有一張帶 sub-task 的 Story。

步驟

  1. 你應該看到：列表出現 WEB Security。
  2. 你應該看到：HR only 底下列出 hr-team 與 Reporter。
  3. 你應該看到：WEB 已套用 WEB Security。
  4. 你應該看到：你在 issue 上會看到設定 security level 的選項。
  5. 你應該看到：Issue 上出現鎖頭或 HR only 標示。
  6. 你應該看到：Kim 看不到（顯示找不到或沒有權限）；Kim 搜尋 WEB 也搜不到它。
  7. 你應該看到：Ana 看得到（她在 hr-team）。
  8. 你應該看到：Sub-task 跟著是 HR only，而且不能單獨改 level。

試試看：改一個設定，觀察差異

T1把 HR only 的 Reporter 拿掉，請 Kim 在 WEB 建一張 Bug，你再把它設成 HR only。看結果
Kim 建立的 issue，Kim 自己看不到了。所以 level 幾乎都要加 Reporter。
T2把 HR only 設成 default level，用 Leo 建一張新 issue、不選 level。看結果
新 issue 自動是 HR only；不在 hr-team 的 Leo 建完就看不到（除非 Reporter 也在成員裡）。
T3在 TEAM 的 Space settings → Work types → 選 Bug → 右上角鎖頭 → 只給 Administrator 看。用 Kim 看既有的 Bug，再請 Kim 建一張新 Bug。看結果
既有的 Bug 不受影響；只有之後新建的 Bug 受限制。TMP 沒有 security scheme，用這種方式限制。
心像錨點：閉上眼睛想一次這個畫面

Watchers 旁邊的鎖頭／Set security level：一張 issue 只能選一個 level。Kim 打開網址是空的，Ana 打開是完整的。

收尾

  • WEB 的 Security → Use a different scheme → None（移除 issue security）。
  • 還原 TEAM 的 Bug 限制；把 default level 取消。
