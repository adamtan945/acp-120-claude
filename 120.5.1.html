3 分鐘速覽

Notification scheme：event → 收件人

  1. Notification schemeJira admin 建立；每個 event 對應收件人；可多 project 共用。
  2. System eventsIssue Created、Updated、Assigned、Resolved、Closed、Commented、Comment Edited、Reopened、Deleted、Moved、Work Logged、Generic Event…
  3. Workflow transition 觸發 eventTransition 的 post function 決定觸發哪個 event（例如 Resolve → Issue Resolved）。
  4. Custom eventSettings → System → Events 建立 → transition post function 觸發 → scheme 設收件人。
  5. 收件人類型Current assignee、Reporter、Current user、Project lead、Component lead、All watchers、user、group、project role、user／group custom field。
  6. 收件人要有權限看不到 issue 的人（Browse、issue security）不會收到。

Custom event（自建）依需求，例如 Group: managers
  1. 建立／編輯Settings → Issues → Notification schemes → Add／Notifications → Add notification。
  2. 選 event 與收件人勾選 event，選收件人類型（role、group、user custom field…）。
  3. 套用Project settings → Notifications → Actions → Use a different scheme。
  4. Custom event建 event（選 template）→ 在 workflow transition 的 Fire event post function 改成該 event → scheme 中加收件人。

動手做

實作 Lab：用 custom event 只在一個 transition 通知 team-leads

約 30 分鐘Jira admin（notification scheme 與 workflow 都要 Jira admin）

第一次做 Lab？先看 Lab 環境準備：用測試站台、準備測試帳號。畫面名稱可能隨 Atlassian 更新而不同，以下以現行畫面為準。

目標：走一次「建 custom event → notification scheme 加收件人 → workflow transition 觸發」三步，看信只在那一個 transition 寄出，再看權限怎麼擋掉收件人。

這個 Lab 對應的考點

Notification scheme 決定 event 寄給誰；custom event 要在 transition 的 post function（EVENT）觸發才會寄；收件人還要能 Browse 該 issue。

準備

  • WEB 改用自己的 notification scheme：在 ⚙ Settings›Work items›Notification schemes 把 WEB 正在用的 scheme（通常是 Default Notification Scheme）複製一份，改名 WEB Notification Scheme，再到 WEB 的 Space settings → Notifications → Actions → Use a different scheme 換成它。
  • WEB 的 workflow 是 WEB 專用、可以編輯的那一個（建 project 時自動產生的那份）。
  • 挑一張 WEB 的 issue：assignee、reporter、watcher 都不是 Leo。Leo 的通知信會寄到你的 email 別名信箱。

步驟

  1. 你應該看到：看到 Issue created、Issue commented、Issue resolved、Generic event 等 system events，每列有狀態（Active／Inactive）。System event 沒有刪除選項。
  2. 你應該看到：清單多了 Lab Escalated，狀態是 Inactive：還沒有任何 notification scheme 或 transition 用到它。
  3. 你應該看到：Lab Escalated 那一列列出 team-leads。回 Events 頁，Lab Escalated 變成 Active。
  4. 你應該看到：儲存成功；所有用這個 workflow 的 space 都會套用這個改變。
  5. 你應該看到：Leo 收到這張 issue 的通知信：他不是 assignee、reporter、watcher，是因為 team-leads 在 Lab Escalated 的收件人裡。
  6. 你應該看到：Leo 通常不會收到：別的 transition 觸發的是原本的 event，那個 event 的收件人沒有 team-leads。
  7. 你應該看到：刪不了（或沒有刪除選項）：只有 Inactive 的 custom event 能刪，它現在被 scheme 與 workflow 用著。

試試看：改一個設定，觀察差異

T1把 Leo 從 WEB 的 Developers role 暫時移除（Leo 不再有 Browse），再走一次 Lab Escalated 那條 transition。看結果
Leo 通常不會收到：team-leads 雖然在收件人裡，但看不到 issue 的人不會收到通知。做完把 Leo 加回 Developers。
T2（想像，不實際做）如果把 team-leads 加在 Issue updated，而不是用 custom event。看結果
WEB 每一次編輯都會通知 team-leads，信件量大增。「只有某個 transition 要通知某群人」就是 custom event 的用途。
T3（想像，不實際做）Leo 只是 WEB 的 project admin（Administrators role），他能改 WEB Notification Scheme 嗎？看結果
不能。Notification scheme 要 Jira admin；project admin 只能看 WEB 用哪個 scheme。
心像錨點：閉上眼睛想一次這個畫面

Workflow 編輯器右側的 details panel：EVENT 下拉選單從 Generic Event 換成 Lab Escalated。事件從轉換出發，收件人寫在 scheme。

收尾

  • 把那條 transition 的 EVENT 改回步驟 4 記下的原值 → Update workflow。
  • 在 WEB Notification Scheme 移除 Lab Escalated 的 team-leads；回 Events 頁確認 Lab Escalated 變 Inactive 後刪除它。
  • 確認 Leo 在 WEB 的 Developers role。
